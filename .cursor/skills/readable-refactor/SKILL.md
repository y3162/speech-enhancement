# 可読性優先の安全なリファクタ

機能は編集前後で同一。最優先は人間が読んで追えること。高い自由度は代償にしてよい。コード量削減はその次。

## 手順

1. **対象を全部読む。** 推測で切らない。エントリポイント、データ定義、呼び出し側、ドキュメントを辿る。
2. **契約を記録する。** 編集前に、後で突き合わせる値を取る。
3. **所見を分類する。** 直す / 残す / 確認してから、を決めてから編集する。
4. **構造を保ったまま直す。** アルゴリズムの書き直しより、重複の抜き出しと未使用の削除。
5. **契約が同じことを検証する。** 一致しない変更は戻す。
6. **結果を事実で報告する。** 直したもの、残したもの、検証した契約を書く。

## 契約（これを変えたら機能変更）

編集前にスナップショットし、編集後に一致させる。

- スキーマ・マイグレーション・CREATE 文
- 公開 CLI のフラグ・意味・成功時の出力
- 中核アルゴリズムの入出力（数値は同一入力で再計算して比較）
- 成功パスのエラー条件（既存 DB がある、必須値が揃っている、など）
- モジュール import 時の副作用（環境変数未設定時の例外型を含む）

一致確認は「同じはず」で済ませず、記録した文字列・値と直接比較する。検証用スクリプトはリポジトリに残さない（ユーザーがテスト追加を頼んだときだけ残す）。

## 分類

**直す（成功パスを変えない欠陥・重複）**

- 到達しうる無限ループ、誤った番兵（`next(it, None)` で値が `None` になりうる）、スキーマに無いフィールド、誰も呼んでいない API、コピーされた同一制御フロー、名前だけ残ったドキュメント参照
- 「バッチする」ように見えて実際は全部メモリに積む、など**見かけと実装が違う**コード。見た目を実装に合わせる（意味は変えない）
- バージョン分岐・形式分岐が二箇所以上あるなら、一箇所にまとめる

**確認する（直すと成功パスが変わりうる）**

- フラグ名と実装が食い違う（例: `--force` が削除ではなく「既存を許す」）
- 共有リソースを複数コマンドが使う
- エラー型や空入力の扱いを「分かりやすく」変えること
- 並び順が永続 ID や決定的出力に効く場合の並列化・走査順

判断できなければ聞く。聞けないなら残して報告する。

**残す**

- 今呼んでいる分岐、ドキュメントと一致している明示データ、領域固有のパーサ（共通化すると追いにくくなるもの）

「将来使うかもしれない」は残す理由にしない。使われていなければ削除する。

## 可読性の判断

- **今の呼び出しに必要な形だけ残す。** 未使用の JOIN / 汎用 ORM / プラグイン点 / 将来用の引数は削除する
- **同じ制御フローが 2 箇所以上**なら、その流れだけをヘルパにする。ドメイン知識（ファイル名規則、レコード組み立て）は元の場所に残す
- **共通化でフレームワークを増やさない。** ヘルパは今の重複より短く、呼び出し側が一度で読めること
- **明示データを生成コードに置き換えない。** ドキュメントと並んでいる定数列は、読みやすさが勝つなら残す
- **名前を再利用しない。** `args` に Parser と Namespace を順に入れる、など
- 既存ファイルの構造・制御フローは、直す欠陥に必要な範囲だけ変える
- コメントアウトや「なぜリファクタしたか」のコメントは書かない
- リファクタと無関係なファイル（エディタ設定など）は触らない
- ドキュメントは事実誤認（壊れたリンク、リネームの取り残し）だけ直す

## 探索の要点

- 定義と使用を grep してから削除する。エクスポートされていてもリポジトリ内に使用が無ければ未使用
- データクラスとスキーマのフィールド名を突き合わせる
- 定数が別定義の名前と重複していないか見る
- 「柔軟に見える」層（クエリビルダ、基底クラス、version dispatcher）は、実際の call site が何種類あるか数える。1 種類ならその 1 種類に縮小する

大規模で全体を読めないときだけ探索用サブエージェントを使う。小さいコードベースは自分で全部読む。

## 検証

- 記録した契約を再生成し、編集前と一致すること
- 壊したくない計算は、小さな入力で期待値を手計算または編集前実装と比較する
- 構文チェック（コンパイル / 対象言語の同等手段）と、主要モジュールの import
- 実データがあれば、メタデータ解析など**編集していない独立実装**と突き合わせる
- UI を触ったときは、見た目だけでなく操作して確認する（ブラウザが使える場合）

## 報告

日本語で、次を短く書く。

1. 直した欠陥（何がどう間違っていたか）
2. まとめた重複・削除した未使用
3. 一致を確認した契約
4. 意図的に残したもの（理由は観察事実だけ。推測で書かない）
